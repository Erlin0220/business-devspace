# Feature Specification: Update Reliability and Upgrade UX

**Feature Branch**: `feature/001-update-reliability-ux`

**Created**: 2026-09-17

**Status**: Draft

**Issue**: [#27](https://github.com/Erlin0220/business-devspace/issues/27)

**Input**: User description: "把旧项目中原本 0.2.7 准备做、但在新的公开仓库中仍未完成的更新可靠性与升级体验优化迁移为当前开发规格；不要重复已经完成的 0.2.7 工作。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 更新崩溃后可立即恢复 (Priority: P1)

作为已经安装 Team DevSpace 的员工，我希望一次更新、托盘或本机生命周期操作即使异常退出，也不会留下长期阻塞后续更新的本机所有权状态；如果另一项真实操作仍在运行，则新的更新必须安全拒绝而不是重复安装。

**Why this priority**: 旧项目的 0.2.7 计划源自真实 Windows 自动更新故障。该故障会让受最低支持版本约束的客户端无法完成升级，直接影响远程工作恢复，因此优先级高于纯展示优化。

**Independent Test**: 可以通过启动一个持有本机更新/生命周期所有权的独立进程、强制终止该进程，再立即发起相同操作来验证。崩溃后的新操作应快速恢复；而在真实所有者仍存活时，第二次操作必须返回产品级“本机操作进行中”状态且不启动第二个安装器。

**Acceptance Scenarios**:

1. **Given** 一个进程正在持有更新或生命周期操作所有权，**When** 该进程异常退出且没有安装器接管事实，**Then** 后续操作无需人工删除锁文件或等待陈旧超时即可恢复。
2. **Given** 一个更新仍由真实进程执行，**When** 第二个手动或自动更新并发到达，**Then** 第二个请求被安全拒绝或延后，且最多只有一个安装器交接被创建。
3. **Given** 更新辅助能力内部发生所有权错误，**When** 托盘和核心 Runtime/Bridge/Tunnel 已健康运行，**Then** 更新失败只影响更新表面，不得导致核心连接被退出或回滚。
4. **Given** 设备从旧版本升级并残留历史更新锁工件，**When** 新版本首次执行更新检查或安装，**Then** 旧工件不得永久阻止新的安全所有权机制。
5. **Given** 系统已经记录了尚未解决的安装器尝试，**When** 持锁进程消失后再次申请更新，**Then** 系统仍以持久化安装尝试事实阻止重复安装，不得把“锁已释放”等同于“安装已结束”。

---

### User Story 2 - “稍后”之后仍能自然继续更新 (Priority: P2)

作为发现可选新版本的员工，我希望“稍后”只表示暂时关闭这一次确认，而不是隐藏更新、自动安装或进入不清楚的状态；之后我应能从现有软件更新入口很容易地继续安装。

**Why this priority**: 旧 0.2.7 讨论明确记录了“点了稍后以后怎么再次安装”的体验问题。当前公开仓库已经具备更新说明和确认弹窗，因此剩余价值在于把“稍后”的语义与后续入口说明清楚，而不是再造一套提醒系统。

**Independent Test**: 手动检查发现新版本后点击“稍后”，确认没有安装发生、更新入口仍明确显示可用版本；随后通过现有更新按钮或再次手动检查，在不超过两次用户操作内重新打开同一目标版本的确认流程。

**Acceptance Scenarios**:

1. **Given** 手动检查发现一个可选新版本并打开确认框，**When** 用户点击“稍后”，**Then** 本次确认关闭且不会下载后激活安装，页面明确告诉用户可以从软件更新入口继续。
2. **Given** 用户刚刚对当前可选版本点击“稍后”，**When** 后台低频检查再次看到同一版本，**Then** 不自动重复弹出确认框，更新可用状态仍保持可见。
3. **Given** 一个可选版本仍然是当前目标，**When** 用户点击“更新并重新连接”或显式再次检查更新，**Then** 同一目标版本的确认流程重新打开并继续使用该版本的更新说明。
4. **Given** 管理员发布了比此前“稍后”版本更新的目标版本，**When** 客户端刷新更新状态，**Then** UI 展示新的目标版本，不把旧版本的“稍后”当成对新版本的隐藏决定。
5. **Given** 更新说明暂时无法读取，**When** 用户重新打开确认流程，**Then** 已签名更新仍可确认，且完整说明入口/失败提示不会误导为安装失败。

### User Story 3 - 最低支持版本到期时明确引导升级 (Priority: P2)

作为受企业最低支持版本策略约束的员工，我希望在策略生效前知道最低支持版本和生效时间；在当前版本已经停止支持后，我希望看到明确、持续且可操作的升级提示，同时仍可使用本机设置、诊断和更新恢复能力。

**Why this priority**: 最低支持版本会真正阻止新的远程工作。如果本机只展示普通“有新版本”状态，用户容易把授权拒绝误判为网络或服务故障。该体验必须与既有 Gateway 门禁语义一致，但不能再造第二套强制更新机制。

**Independent Test**: 用同一个客户端分别投影“宽限期中”和“宽限期已过”两种策略。宽限期中必须显示最低版本和明确生效时间；到期后必须持续显示“当前版本已停止支持/需要升级”的高显著提示和直接更新入口，同时诊断、日志、本机设置及更新操作仍可进入。

**Acceptance Scenarios**:

1. **Given** 管理员已经设置未来生效的最低支持版本，**When** 客户端读取策略，**Then** 软件更新页面明确显示最低支持版本和本地化的生效时间，但不声称当前远程工作已经被阻止。
2. **Given** 最低支持版本的宽限期已经结束且当前版本过旧，**When** 用户打开 Control Center，**Then** UI 持续说明当前版本已停止支持、升级可恢复新的远程工作，并提供直接的软件更新操作。
3. **Given** 当前版本已经被最低支持策略限制，**When** 用户关闭更新确认框或离开软件更新页面，**Then** 必需升级提示仍保持可发现，不会被“稍后”永久隐藏。
4. **Given** 当前版本已经被最低支持策略限制，**When** 用户需要排障或恢复更新，**Then** 本机设置、日志、诊断和更新恢复仍可使用；最低版本策略不得把这些本地恢复入口一起禁用。
5. **Given** 自动更新因远程工作或本机操作繁忙而延后，**When** 用户查看更新状态或客户端重启，**Then** UI 保留可理解的延后原因和后续重试状态，不把延后显示成“已经更新”或重新等待一个完整检查周期。

### Edge Cases

- 所有权进程恰好在安装器交接写入前、写入后或启动系统安装器后崩溃时，持久化安装尝试事实必须决定能否重试，不能只根据本机锁是否存在判断。
- 旧版本留下的锁目录、锁文件或其他历史工件与新版本共存时，升级不得误删未知用户数据，也不得让旧工件继续成为活动所有权事实。
- 手动确认框打开期间管理员改变 stable/auto 目标时，旧确认不得静默安装新的目标版本。
- 当前 stable 被管理员回退时，不得因为本功能自动降级已经安装的客户端。
- 系统时间变化、时区变化或宽限期刚好跨过生效时间时，提示必须以当前策略事实重新计算，不能依赖已经过期的展示状态。
- macOS 已准备更新但仍等待系统授权时，不得因为重启或周期检查反复重新准备同一个安装。
- 更新说明源不可用、更新策略临时不可用或本机 UI 打不开时，核心 Runtime/Bridge/Tunnel 的健康状态不得因此被破坏。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 让更新检查、更新应用和本机生命周期互斥在所有者进程退出或崩溃后自动释放，不依赖人工清理或等待陈旧租约超时。
- **FR-002**: 系统 MUST 在真实所有者仍存活时保持互斥；并发第二次更新不得重复下载后激活安装器或创建第二个安装交接。
- **FR-003**: 系统 MUST 将并发/繁忙状态转换为稳定的产品级状态与用户消息，不得把底层锁实现的原始异常字符串作为正常用户反馈。
- **FR-004**: 系统 MUST 继续把既有安装尝试/安装结果作为跨进程和跨重启的防重复事实；所有权释放本身不得清除或绕过该事实。
- **FR-005**: 更新所有权、检查、缓存清理或展示层故障 MUST 与健康的 Runtime、Bridge、Tunnel 和其他核心生命周期隔离。
- **FR-006**: 从使用旧所有权机制的已安装版本升级时，历史锁工件 MUST 不会永久阻塞新版本；迁移不得通过递归删除未知目录来达成。
- **FR-007**: 临时的系统级更新交接资源 MUST 在完成、失败或过期后有明确的自动收敛边界，避免正常更新长期积累无用系统任务。
- **FR-008**: 对可选更新点击“稍后” MUST 只关闭当次确认，不得启动安装、关闭更新发现或改变管理员推广策略。
- **FR-009**: 用户点击“稍后”后 MUST 仍能从现有软件更新入口在不超过两次显式操作内重新进入同一目标版本的确认流程。
- **FR-010**: 后台更新检查 MUST NOT 因同一个可选版本反复自动弹确认框；确认弹窗继续由用户的显式更新操作触发。
- **FR-011**: “稍后”决定 MUST NOT 隐藏随后发现的更高目标版本；版本变化后 UI 必须展示当前真实目标。
- **FR-012**: 最低支持策略处于宽限期时，客户端 MUST 展示最低支持版本和明确的生效时间，并区分“未来会受限”与“当前已经受限”。
- **FR-013**: 当前版本已经低于生效的最低支持版本时，客户端 MUST 持续展示明确的“当前版本已停止支持/需要升级”信息和直接更新入口；该状态不得被一次“稍后”永久隐藏。
- **FR-014**: 最低支持版本限制 MUST 继续只约束既有策略定义的新远程工作；本机设置、日志、诊断、暂停/恢复所需的恢复路径和更新恢复能力保持可用。
- **FR-015**: 自动更新延后 MUST 保留实际目标版本、延后原因和后续重试语义；客户端重启不得无条件把已经到期的重试重新推迟一个完整检查周期。
- **FR-016**: 更新和升级 MUST 保留既有 Device identity、Access Key/binding、Current Project Root、desired remote-access pause state、签名更新元数据校验、包大小/哈希校验及安装器恢复边界。
- **FR-017**: 本功能 MUST 复用现有客户端拉取、签名更新目录和现有平台安装器，不得引入新的推送通道、后台守护服务、第二套安装器状态机或新的高频 Gateway/D1 心跳。
- **FR-018**: 实现 MUST 提供确定性的进程崩溃、并发更新、旧工件兼容、可选更新“稍后”、最低支持版本两阶段展示及自动更新延后回归测试，并在发布前沿用现有原生平台验收门禁。

### Key Entities

- **Local Operation Ownership**: 某一安装目录当前是否存在真实、仍存活的更新/生命周期所有者。它只负责同一时刻的互斥，不代表安装已经成功或失败。
- **Installer Attempt**: 跨进程/跨重启保留的安装交接事实，包括目标版本、尝试身份、开始时间和当前阶段；它是防止锁释放后重复启动安装器的持久化依据。
- **Update Policy Projection**: 当前客户端看到的 stable、auto、minimum supported、生效时间以及基于当前版本计算出的 available/required 状态。
- **Automatic Update Outcome**: 自动更新最近一次针对实际目标版本的结果，包括已交接、等待授权、因远程工作/本机操作延后、失败以及下一次重试语义。
- **Optional Update Prompt State**: 当前页面中的一次性确认交互。它不是管理员策略，也不是需要服务器持久化的“忽略版本”决定。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 持有本机更新/生命周期所有权的测试进程被强制终止后，下一次合法操作在 5 秒内可以重新获得所有权，不需要修改锁工件时间戳或人工删除文件。
- **SC-002**: 在确定性并发测试中，无论同时发起多少个相同更新申请，最多只有一个安装器交接被创建，其余请求全部得到稳定的 busy/deferred 结果。
- **SC-003**: 更新与生命周期的正常用户反馈中不再出现底层锁库原始错误；相关故障测试不导致健康的 Tray/Runtime/Bridge/Tunnel 因更新辅助错误而退出。
- **SC-004**: 对可选版本点击“稍后”后不会发生安装，也不会由后台检查再次自动弹框；用户从当前 Control Center 在两次以内显式操作即可重新打开更新确认。
- **SC-005**: 最低支持版本生效前和生效后两种状态都能在自动化 UI 验证中被明确区分；生效后升级入口持续可见，同时本机设置、日志、诊断和更新恢复入口仍可操作。
- **SC-006**: 自动更新因远程工作或本机操作延后后，重启客户端仍保留正确的目标/延后状态并按既有短周期重试语义继续，而不是重新等待完整后台检查周期。
- **SC-007**: 受影响的单元/集成/UI 回归测试全部通过，并在进入新版本 stable 前继续满足现有 Windows x64、Linux x64、macOS arm64、macOS x64 原生候选验收要求；Windows 跨版本验收覆盖旧 updater 基线到新候选的恢复路径。
- **SC-008**: 验收确认升级前后的 Device identity、Access Key/binding、Current Project Root 和 pause intent 保持一致，且更新签名/大小/哈希验证边界没有被放宽。

## Assumptions

- 当前公开仓库的更新说明读取、手动检查确认弹窗、自动更新调度、signed update catalog、stable/auto/minimumSupported 策略和现有平台安装器均视为已存在基线，本功能只补仍缺失的可靠性/体验边界，不重做这些能力。
- “稍后”的产品语义采用轻量默认：只推迟当前可选更新确认，不建立定时催促、服务器端 snooze 状态或“忽略此版本”策略；用户通过持续可见的更新入口主动继续。最低支持版本已经生效时，必需升级提示仍持续可见。
- 旧私有仓库仅作为历史证据和已验证实现的参考来源；不会合并旧 Git 历史、旧 Release 或 Actions 元数据到公开仓库。
- 本功能本身不授权生产部署、版本策略变更、二进制发布或 stable/auto/minimumSupported 推进；这些仍遵守现有发布和原生验收流程。
- 本功能不新增 D1 schema、公共 Gateway API 或新的员工凭据。
